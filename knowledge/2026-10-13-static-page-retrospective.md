# 静态效果页交付复盘 · 2026-10-13

> 2026-10-14 用户更新：模板复用是首要资产，详见 [当前核心原则](../docs/TEMPLATE-FOUNDATION.md)。本复盘中先单页后模板的优先级已被覆盖；成本控制、真实验收和交付边界仍有效。

## 用户目标和反馈

用户希望先获得一个可直接打开查看效果的静态 HTML，使用本地麻将产品资料参考 Givingli 的设计，并顺便保存可复用素材。用户曾提出 React、并行代理和素材同步，但随后反复收敛要求为先交付静态成品，不部署，公开美元价格，提供邮箱联系。

用户反馈：流程和重复审查过重，消耗接近 20% 额度；双击 index.html 只有未加载样式的页面。额度比例是用户反馈，未取得逐项消耗账单，不作为工具计量结果。

## 事实与原因

1. 交付错位：实现了 Astro + React 的静态托管工程，却没有交付经 file:// 验证的离线预览包。静态托管不等于双击 HTML 可用。
2. 已检查的构建文件使用 /_astro/ 和 /assets/ 根相对路径，在 file:// 下不能正确定位旁边资源；React 交互还依赖模块加载，不能假设只修改路径即可全部恢复。
3. 流程扩张：多轮规格、实施、审查、复审，加上定价审核、图片多规格、框架兼容和 Sites 适配，挤占了先交付视觉效果的工作。
4. 验证错位：检查了构建、数据和 HTTP 预览，但未按用户双击文件的方式验收。26 项测试通过不能支持“交付全部完成”的结论。
5. 执行返工：曾并行运行写入同一 dist 的构建导致竞争；另有测试夹具缺少品牌文件的问题。不能把所有失败归结为单一原因。
6. 范围说明不足：mailto 只打开访客邮件软件，需访客主动发送；未建立后台收件服务或验证邮箱实际收到。
7. 内容质量：面向买家的页面混入内部制作、素材审核说明；没有充分验证参考页布局及交互保留程度就宣称定稿。

责任在智能体的范围控制、实现选择、验收和交付表述，不能归咎于用户选择插件。并行请求是为了提速，不等于授权无限增加流程。

## 后续执行约定

- 默认首件交付为可双击运行的 index.html + assets 文件夹；需要便于转发时可提供单文件版。素材使用本地路径，CSS 与简单脚本内联或采用本地文件可运行方式。
- React 工程可作为复用源，但必须另行输出满足预览要求的成品。不得要求用户启动服务才能验收首版效果。
- 先复用或建立最小模板，与首个品牌实例一起实现；品牌数据和主题素材独立配置；做一次对应交付环境的必要检查后交付。
- 模板、组件、数据结构和调用说明优先沉淀，AI 绘图素材随实例积累；不扩大为与当前需求无关的平台。同步、部署、支付、后台询盘等按当前授权范围推进。
- 简单单页默认一个主代理。避免多代理反复审查、反复读取上下文和已通过检查的重复执行；对共享输出的命令串行执行。
- 用户明确收敛范围时立即调整，不因已启动的技能流程而继续扩大工作。用户明确要求优先于技能惯例。
- 交付说明必须说明打开方式、文件位置、实际检查和已知限制。file:// 效果、HTTP 效果、邮件客户端打开、服务端接收和实际收件分别陈述。
